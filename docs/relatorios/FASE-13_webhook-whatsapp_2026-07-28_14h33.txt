--------------------------------------------------------------------------------
O QUE FOI IMPLEMENTADO
--------------------------------------------------------------------------------

Variáveis de ambiente novas (src/config/env.ts, validadas via zod):
  META_APP_SECRET   (min 10 caracteres)
  META_VERIFY_TOKEN (min 6 caracteres)

Corpo bruto preservado no parser (server.ts):
  app.use(express.json({ verify: (req, _res, buf) => { req.rawBody = buf } }))
  Aditivo — req.body de todas as 9 rotas existentes continua idêntico.
  req.rawBody (Buffer) passou a existir em toda requisição, usado só pelo
  webhook, pra validar a assinatura HMAC do Meta (que precisa dos bytes
  exatos, não do objeto já parseado).

Schema novo:
  enum MessageDirection { IN, OUT }
  model WhatsappConversation { id, phone @unique, botPaused, lastInboundAt,
    createdAt, updatedAt }
  model WhatsappMessage { id, conversationId, waMessageId @unique,
    direction, rawPayload (Json), createdAt }

  waMessageId @unique é o que garante idempotência: o Meta reenvia webhook
  que não recebeu 200 a tempo (com backoff, por até 36h); a segunda
  tentativa colide na constraint de unicidade e é tratada como sucesso
  silencioso (mensagem já processada), não como erro.

Módulo backend/src/modules/whatsapp/:
  whatsapp.service.ts   — isValidSignature() com crypto.timingSafeEqual
                           (comparação em tempo constante, evita timing
                           attack), findOrCreateConversation(),
                           storeInboundMessages().
  whatsapp.controller.ts — verify() (handshake GET do Meta) e receive()
                           (POST, responde 200 imediatamente, processa
                           depois — reenvio duplicado é o cenário que
                           waMessageId único já cobre).
  whatsapp.routes.ts    — GET/POST em /api/webhook/whatsapp.

--------------------------------------------------------------------------------
PROVA REAL (arquivos citados acima)
--------------------------------------------------------------------------------

a) GET verify com token correto → 200, corpo = challenge exato ("teste123").
   GET verify com token errado → 403.
b) POST com assinatura HMAC válida → 200 imediato. Confirmado no banco:
   WhatsappConversation criada (phone 5531988887777) e WhatsappMessage
   gravada (direction IN, waMessageId correto).
c) POST com assinatura inválida (64 zeros) → 401. (Este é o teste mais
   importante da fase — se desse 200, significaria que o corpo bruto não
   estava sendo capturado corretamente.)
d) Reenvio do mesmo waMessageId, mesma assinatura → 200, mas contagem de
   mensagens ANTES e DEPOIS idêntica (1 e 1) — idempotência confirmada.
e) npm run build sem erro; GET /api/menu (rota preexistente) continuou
   respondendo 401 normalmente sem token; POST /api/auth/login continuou
   parseando req.body normalmente (401 de credencial inválida, não erro de
   parsing) — confirma que a mudança no express.json() foi aditiva e não
   quebrou nenhuma rota existente.
f) npx prisma migrate status → 5 migrations aplicadas, schema em dia.
   Migration gerada contém só CREATE TYPE/CREATE TABLE novos — nada mexendo
   em tabela existente.

Nota registrada no arquivo de prova: uma tentativa de subir o servidor bateu
