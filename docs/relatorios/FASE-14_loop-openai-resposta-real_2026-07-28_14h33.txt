--------------------------------------------------------------------------------
OBJETIVO
--------------------------------------------------------------------------------

O bot passa a responder de verdade ao cliente, usando cardápio/bairros/config
reais do banco e os 4 schemas de function calling em modo `strict`. Nenhuma
função ainda cria/consulta/cancela pedido de verdade, EXCETO
`transferir_para_humano`, que já silencia o bot pra valer. Criar pedido real
ficou pra Fase 15 (que, por sua vez, foi redirecionada pra Embedded Signup —
ver relatório da Fase 15).

--------------------------------------------------------------------------------
O QUE FOI IMPLEMENTADO
--------------------------------------------------------------------------------

Variáveis de ambiente novas: OPENAI_API_KEY, OPENAI_MODEL (default
"gpt-5.1-mini", explicitamente marcado como placeholder não testado — ver
pendência abaixo), META_ACCESS_TOKEN, META_PHONE_NUMBER_ID.

Schema: WhatsappMessage ganhou o campo `content` (String?) — texto legível
extraído da mensagem recebida ou gerado pelo bot, usado pra montar o
histórico mandado à OpenAI. rawPayload continua guardando o payload bruto.

Módulos novos em backend/src/modules/whatsapp/:
  whatsappRateLimit.ts    — isRateLimited(phone): true se > 20 mensagens IN
                             nos últimos 10 minutos. Se true, não chama a
                             OpenAI (resposta fixa, sem custo).
  promptBuilder.ts        — buildSystemPrompt(now?) monta o system prompt
                             com dado vivo (config, cardápio, bairros ativos,
                             isEffectivelyOpen, isDeliveryTimeBlocked),
                             convertendo Decimal→number explicitamente.
  systemPromptTemplate.ts — texto exato colado de BOT-WHATSAPP-
                             PROMPT.md, sem parafrasear.
  conversationHistory.ts  — getRecentHistory(conversationId), TTL de sessão
                             de 1h avaliado de forma preguiçosa (sem cron):
                             se a sessão anterior foi há mais de 1h, a busca
                             não traz mensagens antigas, e isso já é o
                             comportamento certo de sessão nova.
  openaiClient.ts         — callOpenAI() via fetch nativo (Node 18+, sem
                             axios/node-fetch novo).
  tools.ts                — os 4 schemas de function calling (criar_pedido,
                             consultar_pedido_ativo, cancelar_pedido_ativo,
                             transferir_para_humano) em modo strict.
  sendMessage.ts           — sendWhatsappText() via Graph API, grava a
                             mensagem OUT no banco depois do envio.

dispatchToolCall(): só `transferir_para_humano` toca dado real (marca
botPaused: true, loga [WHATSAPP_BOT_HANDOFF]). As outras 3 funções (
criar_pedido, consultar_pedido_ativo, cancelar_pedido_ativo) retornam stub
("ainda está sendo configurado por aqui") e logam
[WHATSAPP_BOT_STUB_CALL] com os argumentos extraídos, sem tocar em Order.

Endpoint novo: PATCH /api/webhook/whatsapp/conversations/:id/resume
(GARCOM, CHAPISTA, ADM, TI) — destrava conversa pausada.

receive() ligado fim-a-fim: grava a mensagem IN, verifica botPaused, verifica
rate limit, monta prompt + histórico, chama a OpenAI, despacha tool call ou
usa a resposta em texto livre, envia via WhatsApp, com fallback de mensagem
de erro pro cliente se qualquer etapa falhar no meio (nunca silêncio total).

--------------------------------------------------------------------------------
PROVA REAL — 7 cenários testados (docs/verificacoes/2026-07-22-fase-14-loop-openai.txt)
--------------------------------------------------------------------------------

1. "oi" com trailer fechado → saudação correta informando que está fechado,
   sem tool_call. (Envio real ao Meta falhou por credencial de teste — Meta
   ACCESS_TOKEN/PHONE_NUMBER_ID ainda eram placeholders nesse teste, erro
   OAuthException esperado e sem relação com a lógica da fase.)
2. "vocês entregam em Alterosa 1?" (bairro real ativo) → resposta bate
   exatamente com bairro/taxa reais confirmados por query direta em
   Neighborhood.
3. Bairro inventado ("Jardim das Estrelas Distantes") → modelo chamou
   transferir_para_humano corretamente, motivo BAIRRO_FORA_DA_LISTA,
   botPaused: true confirmado por query.
4. Mensagem nova pro mesmo telefone, sem destravar → NENHUM log novo (nem
   de resposta, nem de falha) — confirma que `if (conversation.botPaused)
   continue` bloqueia antes de qualquer custo de API.
5. Destravar via PATCH .../resume → OpenAI voltou a ser chamada (mecanismo
   de resume funcionando). O modelo insistiu no handoff mais duas vezes
   pela mesma causa raiz (histórico da sessão ainda continha a pergunta de
   bairro não resolvida) — documentado como comportamento do modelo dado o
   contexto, não falha do endpoint de resume.
6. "quero pedir 2 X-Tudo" → tentativa inicial rodou antes das 18h (trailer
   fechado de verdade no horário real), então o cenário foi reproduzido com
   um parâmetro opcional `now` em buildSystemPrompt (só usado pelo teste
   direto, nenhuma rota HTTP aceita horário fake). Com hora simulada depois
   das 18h: fluxo completo em 3 turnos (monta pedido → resume e pede
   confirmação → só chama criar_pedido após "sim, pode confirmar!").
   Extração correta: quantidade=2, nome_item="X-Tudo", tipo=RETIRADA,
   bairro/endereco null (correto pra retirada), forma_pagamento=PIX. Stub
   logado, nenhum dado real tocado.
7. Rate limit: 20 mensagens semeadas direto no banco (sem gastar chamada
   paga) + 1 real via webhook → nenhuma chamada à OpenAI na 21ª mensagem.

--------------------------------------------------------------------------------
ACHADOS REAIS DOCUMENTADOS NO TESTE (não escondidos, não "consertados por
conta própria" — registrados como o próprio doc de fase manda)
--------------------------------------------------------------------------------

1. BUG DE ADERÊNCIA DO MODELO AO CAMPO TRAILER_ABERTO: no cenário 6, com o
   campo {{TRAILER_ABERTO}} corretamente resolvido como "aberto", o modelo
   respondeu "estamos fechados" nas 3 primeiras tentativas (14:15, antes das
   18h) — aparentemente recalculando por conta própria a partir do texto
   estático "funcionamento: terça a domingo, a partir das 18h" em vez de
   confiar no campo explícito. Reproduzido 3/3. Isso é exatamente o tipo de
   erro que a seção 2 do PROMPT.md avisa que `strict: true` NÃO cobre
   ("garante a forma do JSON, não o conteúdo") — mas aqui nem chegou a
   tentar function call, é a camada de texto livre divergindo do dado vivo.
   CONFIRMADO como causado pelo horário real (antes das 18h) no reteste com
   `now` simulado depois das 18h — o modelo parou de dizer "fechado"
   corretamente. Fica registrado como item da pendência "Ainda em aberto:
   modelo de LLM" do PROMPT.md — merece atenção antes de considerar o fluxo
   de criar_pedido validado ponta a ponta em horário real de operação.
2. OFF-BY-ONE NO RATE LIMIT: o doc de fase 14 dizia "a partir da 22ª
   mensagem, bloqueia". O código real (`count > MAX_INBOUND_PER_WINDOW`,
   MAX=20) bloqueia já na 21ª, porque storeInboundMessages() grava a
   mensagem atual ANTES do loop checar isRateLimited() — a mensagem
   corrente já conta pra si mesma. Não foi corrigido nesta fase porque o
   próprio doc já registra que "o número certo só se decide com uso real";
   tratado como nota de comportamento observado, não uma correção aplicada
   sem aprovação.

PENDÊNCIA QUE FICA REGISTRADA (do próprio doc de fase)
--------------------------------------------------------------------------------

O valor de OPENAI_MODEL em produção precisa ser decidido com teste real
(pelo menos 10 transcrições reais de pedido — gíria, erro de digitação,
cliente mudando de ideia) antes do lançamento. O default do .env é só
placeholder, não recomendação.
